# Feature status

The reference projects are [Spicy Lyrics](https://github.com/iPixelGalaxy/spicy-lyrics/tree/dev) and [Spotify Plus](https://github.com/iPixelGalaxy/spotify-plus). Their JavaScript extensions are not loaded into SpotiFlex. The desktop uses a Tauri/React interface backed by Rust services; the optional egui interface remains available.

Spotify's public API does not expose playlist folders. Local folders are maintained by SpotiFlex and do not change the user's Spotify folders. The [2026 development-mode changes](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide) also restrict reading playlist contents to playlists the user owns or collaborates on. Other playlist names can still appear in the library even when their contents cannot be fetched through this API.

Controls for modifying Spotify's own web menus, Spicetify developer tools, and injected experimental-feature dialogs do not apply to this standalone client.

Playback regression tests reproduce buffer starvation during a 150 ms producer scheduling gap and a two-second lyric rewind after delayed decoder feedback. The output queue now retains 250 ms of audio, native position observations subtract queued output latency, and backward drift corrections preserve forward lyric motion. Explicit backward seeks still apply immediately. These checks do not establish audible playback quality on another computer.

The native clock stops advancing after 500 ms without a fresh observation. Repeated song positions hold lyrics during narration or buffering. Remote playback retains its clock between Web API polls.

Desktop output defaults to This computer. Incoming playback updates do not change the selected output; other devices remain selectable in the device menu. Native Play restores the saved or current song when the connection has no loaded track, including after reconnects and unrelated transport commands. Stopped playback clears that loaded state. Saved sign-in checks show a locked startup screen instead of briefly mounting first-run setup.

Pause retains the bounded 250 ms output queue so unpause can use already decoded audio. Stop, paused seeks and explicit track loads discard that queue. Paused and resumed lyric positions account for retained output latency. Regression tests exercise silent paused output, immediate buffered resume, stop cleanup and seek cleanup without an audio device.

Ctrl + + (including Ctrl + = and numpad Add) increases interface zoom; Ctrl + - decreases it; Ctrl + 0 resets to 100%. Zoom persists across restarts, supports 75–200%, and works while a text field has focus.

Saved-song resume loads the queue and saved position in one native request. After audio sign-in, the saved track is prepared at that position without activating this device or starting playback. DJ preparation reads the existing session and matches the saved track occurrence; it does not consume a fresh selection. Matching pending audio downloads are reused. Late preparation cannot replace a playback selection. Play can still wait on Spotify when preparation has not finished.

Live Windows resume checks on 2026-10-18 measured 161 ms after three seconds of idle preparation, 648 ms when Play followed native readiness immediately, and 791 ms for a prepared DJ resume. Earlier saved-position startup samples took 1,079–1,829 ms; ordinary resume first started at zero before a second seek. The updated checks started at the saved position, kept playback paused throughout idle preparation, and produced an unmuted Windows audio-session signal. These samples use one machine/account and do not guarantee network latency.

Native connection readiness and failures are retained until the matching account completes sign-in. A connection established before the profile check finishes can then accept Play without requiring a manual reconnect. Play retries a failed native connection while preserving the pending selection.

Optional Web API playback polling cannot cancel the authenticated audio session during startup. Closed native control channels trigger reconnection on Play even if the earlier readiness event was never delivered.

DJ prepares one unheard set and its first speech in the background without activating playback. Prepared sets are consumed once by fresh starts or matching next-page requests; restoring an existing DJ session retains its track and position. Music and speech downloads run concurrently. Speech stays in a bounded, account-scoped memory cache; interrupted downloads and temporary failures can retry. Cold requests can still wait on Spotify.

Live Windows checks on 2026-10-18 measured prepared DJ narration starts at 761 ms and 814 ms, against the earlier 5,936 ms baseline on the same machine/account. The second selection changed tracks and produced a Windows audio-session signal. Idle playback stayed paused with an unchanged position while preparation ran. A separate cold-start Play check resumed the saved position without manual reconnection. Cached artist metadata arrived in 6 ms; unseen metadata still depends on network responses. These are observed samples, not latency guarantees.

Metadata context menus target song titles, artist names, album labels/artwork and playlist items. Right-clicking blank row space, hero backgrounds or player controls dismisses them. Human-created playlists and Liked Songs hide the Plays column; album, artist and Spotify-owned playlist statistics remain available.

Album links whose current track lacks an album ID resolve it through native `TRACK_V4` metadata. The native metadata request filter permits that read; a channel-level regression test covers album resolution and preserves the album ID in its result.

Artist and album headers load through native catalogue requests independently of the Web API worker. Known artist names appear as soon as navigation starts. Account-scoped metadata caches retain up to 512 headers with artwork URLs, artist overviews and album details across restarts; cached details render before background refresh. Current music and nearby artist links are prefetched, with six-hour reuse for speculative requests. Shared image decoding warms banners and profile pictures. Album basics render before optional stream-count enrichment; partial updates preserve cached duration and other stream counts. Previously unseen metadata and artwork still require network access.

Read-only verification on 2026-10-18 returned six account-specific Daily Mixes, twenty recent items, personalized release and station shelves, and a five-track DJ session with a next-page URL. A DJ intro was synthesized, downloaded and decoded into 336,384 interleaved samples. The user confirmed DJ playback in SpotiFlex on 2026-10-18. Multi-set continuation and the new fades still need live verification.

Live checks on 2026-10-17 verified native play/pause after repeated click bursts, Spotify Canvas loading as a muted loop (7.25 seconds for High Forever), the current desktop artist header field, and album play counts. Internal Spotify catalogue queries may change; missing data falls back to the public catalogue. Creator IDs resolve to canonical profile handles before opening an isolated native window. Live checks verified Canvas suppresses album ambience and fullscreen exit restores the maximized work area. Native skip testing verified that the displayed track follows the loaded queue. Resume records retain the loaded queue, and track-title album links resolve missing IDs through native metadata. Full fork parity and independent audible-output verification remain unfinished.

Narration transition tests cover stereo fade direction, speech labels during overlap, unchanged music without narration, and seek buffer resets. Connect tests cover direct resume from pause, ignored stopped-session events and clock corrections that must not resume playback. Local pins and recents persist separately for each signed-in account. Discord presence itself has not been verified.

The player DJ button distinguishes click from a 500 ms hold. Click refreshes the DJ selection. Hold or Shift+Enter opens Ask DJ for arbitrary text or voice. Opening the dialog does not start recording. Closing it, cancelling, signing out or switching accounts discards late results. The first-run sign-in modal remains mandatory.

Native request transport uses Spotify's advertised per-item prompt signal and current list revision. Typed text and recognized voice prompts use distinct input values in a bounded UTF-8 protobuf payload. Empty requests, more than 500 Unicode characters and unsupported control characters are rejected. Signals are not automatically retried, responses are bounded and redirects are disabled. Network preparation runs outside the UI thread; account and cancellation checks guard playback handoff.

Live checks on 2026-10-19 accepted separate jazz and energetic 2000s rock requests. The rock request returned 20 tracks with matching rock narration; its next page added five tracks with no repeated occurrence IDs. Re-reading that page returned the cached result without another signal. Requested music and speech come from the native list response: the legacy DJ context URL returned an older selection and is deliberately bypassed. Prepared contexts clear the earlier DJ cache, and subsequent pages retain their account-bound source. Requested queues resume as saved music after restart; their interactive DJ session and narration do not survive restart. Full request-to-speaker listening verification remains outstanding.

Windows voice capture reads Windows Default microphone directly through CPAL/WASAPI. It mixes channels and resamples to mono 16 kHz PCM for local Whisper small.en decoding. Windows dictation and its confidence scores no longer gate recording or recognition; “Play Rammstein” now reaches the local model even when Windows cannot recognize that artist. Audio stays in memory. There are no artist-specific runtime corrections.

The verified 190 MB English model preloads once during app startup on a worker. Voice requests reuse that same instance. When weights are missing, startup downloads them from a pinned HTTPS revision, checks the size and SHA-256, and loads only verified bytes. Redirects are limited to approved model-host domains. Startup preparation never opens the microphone. The request dialog shows preparation if necessary, listening, then local recognition. Only the decoded text reaches Spotify; automatic submission never fills the typed draft.

WebRTC voice activity detection classifies acoustic frames without reading words. Sustained speech starts a request; isolated clicks and the deterministic fan/hum fixture do not. Capture stops after 1.2 seconds without detected speech, after eight seconds without speech, or at the 30-second maximum. An eleven-bar white meter follows raw microphone levels independently of recognition. Callback buffering is bounded; stream interruption aborts the request rather than submitting partial audio. Cancellation covers preparation, capture and decoding, with capture reserved until work exits. Background speech can still resemble a request; real microphones and room conditions need further verification.

Synthetic Windows tests cover five artist names, general music requests, noise rejection, cancellation and model-instance reuse without opening a microphone. The tests now exercise raw PCM voice activity detection and local decoding rather than passing through Windows dictation. Browser checks cover the eleven bars, stale events, automatic submission, unchanged typed drafts, focus and sign-out. Live Spotify preparation of the correctly recognized example returned the requested artist in its first eight tracks; audible request playback remains unverified.

A written hold-button reminder appears when DJ narration first starts, separately per account, then becomes eligible again after three days. Spotify responses inspected expose written DJ prompts but have not supplied the requested spoken hold-button instruction. The spoken version remains a gap pending an available narration source; no such playback is claimed.

A live library read on 2026-10-19 returned 36 playlists while the saved library cache was absent. Rebuilding that cache restored all 36 in the running sidebar. The original startup failure was no longer observable after the application closed. Library results now persist in the worker before delivery to the window. A failed load schedules another attempt after 30 seconds, respects Spotify's shared cooldown and keeps the last complete list visible. A regression test covers an initial fetch failure followed by recovery without another login; pagination tests still cover private and collaborative playlists.

Native reconnect stays idle until playback is requested. A same-song takeover claims the local device before accepting decoder positions; the UI starts a new clock observation even when loading and playing events arrive together. Regression tests reproduce the prior 1:17 display against audio at 0:01.2.

DJ transitions duck music under speech rather than fading the final words to silence. Music rises after the spoken line ends. End-of-track waits for submitted PCM to drain before advancing, preserving buffered narration tails. Synthetic audio tests cover audible final syllables and output completion; the revised transitions still need live listening confirmation.

DJ resume records its existing session and track UID rather than converting the current song into a standalone playback request. A skipped track is selected after resolving the session and any required next page. If Spotify regenerated UIDs, the track URI provides a fallback. Old saved files remain readable; recent playback context and passive Connect transfer metadata can recover DJ origin where Spotify still provides it. An expired session starts a fresh DJ selection. Native saved positions use the latest decoder observation so held narration positions do not advance while speech plays.
